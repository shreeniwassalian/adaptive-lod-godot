# Speaker script

## Slide 1

This project asks a narrow question: if the renderer is over budget, can a controller coarsen vegetation detail automatically, in a stable and bounded way, and does that buy frame time? The scene is a Terrain3D forest with about 42 thousand vegetation instances plus a very dense grass field. I compared a fixed-threshold baseline against an adaptive version on the same scene and camera path. The honest summary, which I will build up to, is: the mechanism works and is bounded, the visual change is small, and the measured performance gain is small and only demonstrated in one configuration.

## Slide 2

Rendering cost grows with triangles, draw calls and overdraw. LOD trades detail for cost by swapping to simpler representations with distance. The weakness of a fixed-distance scheme is that it does not know the frame budget: it draws the same detail whether the GPU is at 8 ms or 30 ms. The left side is general concept; the schematic is illustrative, not my meshes. The right side is what I actually built: a baseline with fixed thresholds for trees, grass, bushes and debris, and an adaptive mode that scales those same thresholds with one feedback-controlled bias. I also want to be clear about what is not there: no per-instance importance, no cross-fading, and bushes have no mesh LOD, only density thinning.

## Slide 3

The pipeline has two halves. Along the top is the adaptive part, which only runs in adaptive mode: the GPU render time of the main viewport is smoothed, compared against a target, and a PI controller with rate limits produces one global bias between 0 and 2, which is mapped to a per-category bias. Along the bottom is what runs in both modes: for each tree, grass cell or chunk the policy compares camera distance in metres against thresholds, with hysteresis, and updates MultiMesh tiers under a change budget. With the bias at zero the thresholds are exactly the baseline, so the baseline is the adaptive system with the controller switched off. The snippet is the real threshold code: the effective threshold is baseline divided by one plus bias, but clamped by a floor in metres, so trees closer than 100 m can never be coarser than baseline LOD1. One precise point for the viva: the constraint is expressed as distance floors and per-category caps, not literally as a two-level limit; trees only have three mesh levels, so the coarsest possible step is LOD0 to LOD2, and the floors restrict where that is allowed.

## Slide 4

Five contributions, each with a status I can defend. One: thresholds that move with a controller instead of being fixed. Two: everything expressed in metres, so the behaviour is interpretable. Three: constrained coarsening. Here I need to be exact: what is implemented is distance floors for trees at 60 and 100 metres plus per-category caps, and a self-test shows zero trees within 100 m deviating from baseline at the maximum bias. That is not literally a two-level limit, so I mark it as partly matching. Four: the benchmark harness, with the same path hash and seed, interleaved runs, and full CSV and JSON output; the caveat is that machine state drifted. Five: the trade-off, where I have exact primitive counts and one stress-profile frame-time gain, but no perceptual quality metric yet. And I make no claim of global novelty because I did not do a literature review.

## Slide 5

All numbers come from the project benchmark harness: Godot 4.7.2 in a debug editor build on an i7-8850H with a Quadro P3200, Forward+ on D3D12, VSync off and uncapped. The camera follows a fixed 528 metre path at 8 metres per second with a 10 second warm-up and 60 seconds measured. Baseline and adaptive runs were interleaved. Equivalent conditions: same scene, seed, path hash and resolution. Differences that threaten fairness: the machine GPU state changed between runs, which you can see in normal baseline number 1; the build is a debug editor build; and the results use an earlier controller mapping than the current code. Hardware items such as driver version and RAM were not recorded in the files, so I flag them as missing rather than guess.

## Slide 6

This is the main results slide. In the stress profile at 1440p, two baseline runs and two adaptive runs agree closely with each other: adaptive averages 33.4 FPS against 31.5, a 5.8 percent increase, and mean frame time drops from 31.7 to 29.95 ms, minus 5.5 percent; for frame time lower is better, so a negative change is an improvement. Main-pass primitives fall about 17 percent and draw calls about 10 percent in that profile. At 1080p the picture is different: baseline runs 2 and 3 and the adaptive runs are statistically indistinguishable, about minus 1.5 percent average FPS, so I claim nothing there. Baseline run 1 ran at 104 FPS because the GPU was in a different state; I show it rather than drop it. On the sub-10 FPS question: I checked every recorded run. No adaptive 60 second run has a frame under 10 FPS; the worst adaptive frame is 20.7 FPS. The only sub-10 frame in this series is in baseline number 1. So the severe drops you saw while playing are not in the saved logs. One hypothesis is the first-enable build, which takes roughly 0.7 to 1 second when you switch modes live, but that is untested. Also, the controller never reached its targets: 16.67 ms at 1080p and 8 ms in stress. The performance objective is therefore not achieved; only a small stress-profile gain was measured.

## Slide 8

To conclude. What works: the adaptive mechanism is implemented, bounded by floors and caps, and measured with a reproducible harness. What the data supports: a 5 to 6 percent frame-time gain in the stress profile, no measurable change at 1080p, and a small, localised visual change. What it does not support: that adaptive LOD reaches the frame-time targets, or that it fixes FPS instability. The severe drops I observed while playing are not in the saved logs, so I will not explain them as fact; the first-enable build is my leading hypothesis. Next steps are tuning, cross-fading, release-build profiling and more repeats on an idle machine. The takeaway: adaptive LOD gives a controllable, quality-preserving trade-off, but the benefit on this workload is small because terrain, shadows and the rest of the frame dominate the GPU time.
